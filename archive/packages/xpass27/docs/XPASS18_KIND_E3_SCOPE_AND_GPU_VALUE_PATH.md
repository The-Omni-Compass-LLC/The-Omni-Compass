# XPASS18 E3/E4 scope and value path

## Kind is E3, not electricity evidence
The Kind harness exercises a real Kubernetes API server, scheduler, HPA, metrics-server, service path and bounded Omni writer on containerized workers sharing one host. Its power quantity is a declared harness model. A parked Kind worker remains a Ready container and is not a powered-off server. Therefore Kind results may support software-control, write isolation, restoration, latency/SLO, controller-overhead and modeled-resource claims only. They do not establish GPU joules, RAPL package energy, wall energy, utility-bill savings, or Karpenter product performance.

## Comparator separation
The four-arm simulator's C3 is a documented-behavior Karpenter-style replica. Kind-23 does not execute Karpenter. Native/Watch/Omni on Kind are the valid E3 paired arms. Product claims about Karpenter, CAST AI, StormForge, Turbonomic, OpenShift autoscaling, Borg or Twine require the actual product/system or a separately labeled proxy/model.

## GPU E4 path
The NVIDIA paired harness is the first current path intended to produce device-level physical evidence: requested power limit, enforced readback, device energy, useful work, SLO/guardrail, attribution, Watch zero writes and restoration. Device joules remain distinct from facility electricity. A facility-level electricity percentage requires a wall/PDU/utility-grade boundary and matched useful work.

## Economic interpretation
A measured percentage reduction is economically meaningful only after its measurement boundary is named. Three percent of GPU-device joules, three percent of IT-load energy, and three percent of the facility electricity bill are different claims. The software must report the numerator, denominator, work/SLO condition and measurement boundary before any savings percentage is promoted into a financial claim.
