The founder's order of 23 October 2026: grade the orchestrator (`omni_orchestrator/`, `docs/OMNI_ORCHESTRATOR.md`) at referee
level, sector by sector. The grades below are The Omni-Compass LLC's own reading of its own code and its first showing, written
the way a referee of a systems paper or an underwriter of a product would write them: every grade names what was examined,
what it earned the grade and what it lacks. No outside party has reviewed or approved these grades. The scale: A, the sector
would pass a referee without a request for changes; B, it passes with named changes; C, the mechanism is present and works in
the showing but a referee would not accept a claim on it yet; D, present in name only; F, absent.

| sector | grade | what was examined and what it earned | what it lacks |
|---|:-:|---|---|
| 1. Architecture and provenance | **A−** | Written from scratch on Python's standard library and the compass law; no orchestrator's code in it, the only outside mechanism the kernel's own, declared native under it. Eight pieces, each one file, each file its own statement of what it does. The yardstick written by us from Kubernetes' documentation and named as such everywhere. | Python at every layer: the front and the hands are not built for thousands of requests a second; the pieces have no versioned wire format between them (plain JSON over HTTP, unversioned). |
| 2. Isolation: the walls (`cgroup.py`) | **C+** | Every machine and every unit in its own control group; the CPU quota is written and enforced by the kernel (shown: the units' processor time read from the kernel's counter); the memory limit written where the kernel takes it. A hand that starts again kills what the lost hand left. | Control groups version 1 only (version 2, the default on modern kernels and on GitHub's runners, is not yet read or written); no process, network or filesystem namespace, so a unit sees every other unit; no limit on files, pids or disk; a memory limit the kernel refuses is silently not applied. |
| 3. The machine's hand (`agent.py`) | **B** | The whole life of a unit: start inside its walls on its machine's cores, probe twice a second, ready at the first answer, killed and started again after three missed answers, a crashed unit started again after a wait doubling to 30 s, a task done at exit 0 or failed after three tries, SIGTERM then SIGKILL after 3 s on stop. Shown: a unit killed came back with 0 requests failed; the units kept serving while the control plane was dead. | The hand is one process with no watchdog of its own (a dead hand is detected only by the control plane); its HTTP has no authentication (bound to the loopback only); a unit's stdout log grows without bound; the health probe is HTTP only. |
| 4. The front (`front.py`) | **B−** | One address; one line; one hand per ready unit so a unit works one request at a time and the waiting is measured in one place; a failed answer retried on another unit up to three times; the routes re-read from the control plane's file within 0.2 s; the 50th, 95th and 99th percentiles over 1, 5 and 10 s written every second. Shown: 0 of 4,328 requests failed across the four parts, including a machine's loss. | A single process, the one point whose death stops the service (no second front, no shared address); plain HTTP, no limits on connections or request size, no timeout on a slow client; the line is unbounded; the 30 s answer timeout is fixed. |
| 5. The room rule (`scheduler.py`) | **C+** | A unit goes only where its request fits on a machine awake, so no machine is ever asked for more than it has; pack (Omni) and spread (the yardstick) as two declared rules; a service of two or more units never on one machine alone. Held by unit tests. | Room is counted from requests only, never from the machine's measured busy share: the first showing read exactly this (four units whose quotas sum to a whole core, packed, each answer slower). The engine that stands already has the rule (no replica onto a host 75% busy, `omni_controller/capacity.py`); the orchestrator does not yet. Memory is not counted as room; no affinity, taints or zones. |
| 6. The brain: units (`brain.py`) | **B−** | The compass law on the 95th percentile in the band from 0 to the line; a force up adds units at once, past the wall the most it may; a force down gives back one unit only after three calm beats with nothing waiting; and the floor: never fewer units than the native twin (the yardstick's rule on the same readings). Shown: the units Omni held were the twin's own at every beat; held by unit tests. | The band's line is the operator's declared line (800 ms), so a 95th percentile of 200 ms reads calm while native's is 165 ms: the law reads the line, not native, and only the twin floor ties it to native; no reading of the units' own busy share enters the force; one service only is sensed (one front). |
| 7. The brain: machines (`brain.py`, `control.py`) | **C+** | Machines woken before a unit waits (room for the next step), never fewer than two; parked one at a time after three calm beats, their units moved first and the machine kept if they find no room in 60 s; the kill switch puts every machine back on. Shown: 0 seconds with a unit short of room in the Omni arm; two machines parked; one woken for the seventh unit. | Parking is decided from requests, not from the machines' measured load; the park hold (three beats) is not tied to the boot time, so a climb can wake what was just parked; no model of a real cloud's boot (60 to 90 s) or of its billing granularity; one machine size. |
| 8. The control plane (`control.py`) | **B** | A ledger journaled before every act and replayed on start (shown: killed and started again, 21 lines replayed, every unit taken back as it stood, none started again, 0 requests failed); every hand polled every second, a machine silent three times declared down and its units placed again (shown: 2 units lost, placed again, 0 failed); retiring units out of the routes before they stop; a stray unit stopped; batch tasks in the room the service leaves, yielding to it; the kill switch (shown); one audit line per decision with its reason; a failed check recorded and the next on time. | One instance, no second one, no leader election and no fencing (two control planes would fight); the journal grows without bound (no compaction); machine state "booting" is a timer, not a real machine; the HTTP to the hands is unauthenticated plain text; the whole loop is a single thread with a thread pool for the hands, not measured under hundreds of machines. |
| 9. The workload and the clients (`workload.py`, `load.py`) | **A−** | Every answer checked against a digest the client computes itself before the first request, so a wrong answer cannot pass as work; closed-loop clients with a thought time, stepping by one, the organism's own load shape; every request one row of the record. Shown: 0 wrong answers in 4,328. | One kind of work (processor only; no memory, disk or network load); the clients run on the same host as the units (the fourth core), so a saturated host would slow the clients too. |
| 10. The method of the showing (`tools/orchestrator_show.py`) | **C+** | Both arms the same clients, the same steps, the same machines; readings step by step as pairs with the exact Student t interval; every gauge read by the one key; every number from the showing's own files (requests, timeline, audit, the kernel's counters); the report built from the files, reproducible from them. | One run of each arm, not the three-run rule; six steps of 15 s in the quick form; the two arms run one after the other, not at once; one host, with two "machines" sharing one core, so a packed core's contention is partly the rig's; no preregistration before the run; no untouched seeds. |
| 11. The reading and its honesty | **A** | Every row shown, the LOSS rows first: work −11.1% LOSS, the 95th percentile +23.8% LOSS, machines −26.5% GAIN (a cut); the cause found in the files (packing to the whole of a core) and named with the mechanism that answers it, not tuned away; the claim stated exactly (section 4 of the page) and what it does not establish. | The cause is read from the files and the mechanism, not yet proven by a run with the fix beside a run without it. |
| 12. Recovery drills | **B** | Four drills with the clients running through all of them: a unit killed, a machine lost and repaired, the control plane killed for 10 s and started again, the kill switch on and off; 1,507 requests, 0 failed, 0 wrong. | No drill of the front's death (the one point that would fail); no drill of two machines lost at once, of a hand that lies (reports ready while the unit hangs), of a full disk, of clock skew; recovery time is read from the timeline, not measured as a gauge. |
| 13. Security | **D** | Nothing listens off the loopback; the hand kills what a lost hand left; the kill switch is a file only the host's user can write. | No authentication or authorization on any endpoint; no encryption; no secrets handling; a unit runs as the same user as the hand (as root in the showing); no audit of who pressed what (the control API of the engine, `tools/omni_control.py`, `docs/OBSERVABILITY.md`, is not yet wired to this orchestrator). |
| 14. Tests | **C+** | 11 unit tests: the room rule (fit, awake only, pack, spread), the yardstick's arithmetic, the twin floor, fail-up, the hold before a give-back, the machine count, the ledger's replay, the checked work. Every test runs in under a second. | No integration test under `verify.py` (the showing is run by hand); the hand, the front and the control loop are tested only by the showing; no property tests, no fault injection in tests; coverage not measured. |
| 15. Documentation | **B** | One page (`docs/OMNI_ORCHESTRATOR.md`): what it is, piece by piece, the first showing's every number, the cause of each LOSS, what it covers and does not, the claim exactly; every file's docstring states its mechanism; the report explains its rig and its yardstick. | Not yet bound into the three manuals; no wiring recipe for a real fleet (many hosts); no operator's run book (start, stop, replace a machine, read the audit). |
| 16. Functional coverage against an orchestrator's duties | **C** | Twelve duties covered and shown: desired state kept and survived; placement by room; a unit's life; health checks; processor and memory walls; one address with the load shared; units scaled with the load; machines scaled; batch beside a service; a machine lost; a kill switch; an audit. | Seven not yet: many hosts over a network (the hands already speak HTTP; unshown); container images and a registry (units are processes); network isolation, names and encryption; storage that follows a unit; rolling updates; secrets, users and permissions; and the comparison against Kubernetes itself on the same organism (the kind rig). |
| 17. Performance against the yardstick (first showing) | **C** | The same units on fewer machines (−26.5%); 0 failures; the brain's decisions explainable line by line. | Less work (−11.1%) and slower answers (+23.8% on the 95th percentile): LOSS by the key, the trade of packing on this rig, with the mechanism fix named but not yet run. A C until a run with the fix reads no LOSS against the yardstick, and the real comparison against Kubernetes runs. |
| 18. Evidence class and standing | **L (live software), one host, one run** | Real processes, the kernel's own counters, every answer checked. | Not a benchmark result: no three runs, no untouched seeds, no GitHub run with its commit named yet (the workflow is the next step), no run against Kubernetes itself. |

**Overall: B−** as a first-day showing of a mechanism that works end to end; **not production**, and not yet a benchmarkable
claim. The three changes a referee would require before any claim: (1) the room rule counts the machine's measured busy share
(the engine's own 75% rule) and the run is read again with and without it; (2) three runs on GitHub's machines from one named
commit, the yardstick and Omni, archived like every other run; (3) the same organism under Kubernetes itself on the kind rig
beside this orchestrator, four ways as the governors are run. Then security (13) and isolation (2) before anyone runs it on a
machine they care about.
