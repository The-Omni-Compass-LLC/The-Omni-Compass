This is a repair candidate (branches `codex/v7-quota-convey` and `v7-candidate`), not a completed benchmark claim. It carries two conveyance repairs, each found from a v6 run's own files. Main and the ongoing Azure and broad v6 campaign keep their frozen v6 engine. Results from the two versions are never pooled.

The original capacity run 38722001872 tried to raise a pod CPU limit while its namespace CPU quota was already full. The candidate reads each namespace's ResourceQuota CPU-limit hard/used values, obeys the stricter pending spec/status ceiling, and reserves each accepted increase across all target deployments in one conveyance pass. It does not increase or delete an operator quota. PriorityClass scope selectors are matched from pod metadata, without deployment or quota names hardwired into the governor. Unknown quota state, read failures and unsupported scopes preserve native limits for expansion; reductions remain possible. Decreases do not create spendable headroom until observed by Kubernetes.

Kubernetes admission remains authoritative. A concurrent rejected write is audited and does not become an invented conveyance gain. The node's existing CPU cushion, operator CPU floor, security hold, workload schedule and benchmark validity checks remain intact. The separate runner shutdown in the historical run has no established cause and is not claimed fixed by this actuator change.

**One processor conveyed once.** The v6 three-run KEDA table (`results/live/V6_KEDA_REQUESTS.md`) read the pod start wait, mean, +12.5%, +12.0% and +22.7% (EVEN on the three-run rule, LOSS in two single runs). The cause, from the 151 pod starts in its raw files: a start takes longer when the runner's processor is busier, in both arms alike (7.9 s against 8.1 s at 25 to 50% busy, 9.2 s against 9.9 s at 50 to 75%), and only the omni arm reached 75 to 100% busy (20 starts, 12.4 s). On kind every node is a container on one 4-core runner and reports all four cores as its own, so conveyance gave each of three serving pods 3,700m of that one processor. v7 counts a machine's processor once: where every node stands on one host (providerID `kind://`, the same test the replica room uses), the host is the machine, A its CPU once, Q every other pod's requests on all its nodes, P every serving pod on it. No limit is raised while that host is at or over 75% busy or its busy share cannot be read, and on any cluster no limit is raised on a machine where a pod is starting; lowering is never held back, and each hold is written to the audit (`"convey": "held"`). On separate machines the arithmetic is unchanged.

Validation: five shared-host regressions pass (`tests/test_convey_shared_host.py`: the host counted once, a busy or unread host holds, a start holds while lowering proceeds, separate machines keep their own arithmetic, the start test reads the pod). Eight quota regressions pass; the original source fails both the full-quota regression and the admission-rejection regression. Existing conveyance integration checks pass unchanged. A live GitHub trial repeats the original cap 1500m / repetition 4 / 1200-second-per-arm case at the original request rates. Its completion and measured result must be read from its artifact, with any LOSS retained. The trial cannot launch Azure, Google, Amazon or GPUs.

Reference: Kubernetes [Resource Quotas](https://kubernetes.io/docs/concepts/policy/resource-quotas/) and [in-place container resource resizing](https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/).
